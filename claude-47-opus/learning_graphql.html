01

Qu'est-ce que GraphQL ?

GraphQL est un langage de requête pour API et un runtime d'exécution côté serveur, créé par Facebook en 2012 et open-sourcé en 2015. C'est une alternative à REST qui donne au client le contrôle exact des données qu'il reçoit.

📋 Schema-first

Le contrat entre client et serveur est explicite. Une seule source de vérité, typée, auto-documentée via introspection.

🎯 Demande exacte

Le client décrit la forme de la réponse. Pas de sur-fetching (champs en trop), pas de sous-fetching (requêtes en cascade).

🔗 Endpoint unique

Une seule URL /graphql. La requête détermine ce qui est exécuté, pas l'URL.

L'analogie du restaurant

Avec REST, c'est un menu fixe : vous commandez le plat n°7, vous recevez tout ce qu'il contient (même les olives que vous n'aimez pas). Pour la sauce, il faut commander le plat n°12 séparément.

Avec GraphQL, c'est un menu à la carte : vous demandez exactement ce que vous voulez — "un steak saignant, sans olives, et la sauce du plat 12" — en une seule commande.

💼
Question type d'entretien "GraphQL remplace-t-il REST ?" — La bonne réponse n'est pas binaire. GraphQL excelle pour les UIs riches avec des relations complexes (réseaux sociaux, dashboards). REST reste pertinent pour des APIs publiques simples, le cache HTTP natif, ou les endpoints orientés ressources/CRUD basiques.
02

REST vs GraphQL

L'exemple classique : afficher un profil utilisateur avec ses 3 derniers posts et le nombre de commentaires sur chaque post.

🔴 REST — 5 requêtes 
GET /api/users/42
GET /api/users/42/posts?limit=3
GET /api/posts/101/comments?count
GET /api/posts/102/comments?count
GET /api/posts/103/comments?count

Sur-fetching probable (champs inutiles), waterfall de requêtes, latence cumulée.

VS
💖 GraphQL — 1 requête 
query UserProfile {
  user(id: "42") {
    name
    avatar
    posts(limit: 3) {
      title
      commentCount
    }
  }
}

Champs précis, relations imbriquées, payload optimal, en un seul aller-retour réseau.

Tableau comparatif

Critère REST GraphQL
EndpointsMultiples (1 par ressource)Un seul /graphql
Méthode HTTPGET / POST / PUT / DELETEPOST (toujours)
Forme de la réponseImposée par le serveurChoisie par le client
Sur-fetchingFréquentÉliminé
Sous-fetchingFréquent (waterfall)Éliminé
TypageOptionnel (OpenAPI)Imposé par le schema
Cache HTTPNatif (URL)Manuel (Apollo, urql)
Versioningv1, v2, /v3...Évolution via @deprecated
Codes HTTP200/4xx/5xxToujours 200, erreurs dans errors[]
Upload de fichiersNatif (multipart)Spec séparée nécessaire
⚠️
Pièges côté GraphQL Cache plus complexe (pas de cache HTTP), risque de requêtes lourdes (DoS via profondeur/complexité), monitoring moins évident — chaque champ est une "route" potentielle. Ces problématiques font partie des questions avancées en entretien.

Schema & Types (SDL)

Le SDL (Schema Definition Language) est le langage qui décrit la structure de votre API. C'est le contrat partagé entre frontend et backend.

Types scalaires intégrés

Int

Entier 32 bits signé

Float

Nombre à virgule flottante

String

Chaîne UTF-8

Boolean

true / false

ID

Identifiant unique (sérialisé en string)

Custom (ex: DateTime)

Définissables via scalar

Définir des types objets

SDL schema.graphql
# Type personnalisé pour les dates ISO 8601
scalar DateTime

# Une énumération de valeurs autorisées
enum Role {
  USER
  ADMIN
  GUEST
}

# Le ! signifie "non-null" (obligatoire)
type User {
  id: ID!
  email: String!
  name: String
  role: Role!
  createdAt: DateTime!
  # [Post!]! = liste non-null d'éléments non-null
  posts: [Post!]!
}

type Post {
  id: ID!
  title: String!
  content: String!
  author: User!
  comments: [Comment!]!
  publishedAt: DateTime
}

Le triptyque obligatoire

Tout schema GraphQL expose au plus trois types racines :

type Query {
  # Lectures — équivalent des GET REST
  me: User
  user(id: ID!): User
  posts(limit: Int = 10): [Post!]!
}

type Mutation {
  # Écritures — POST/PUT/PATCH/DELETE
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): Boolean!
}

type Subscription {
  # Temps réel via WebSocket
  postAdded: Post!
}

# Input type — utilisé pour les arguments complexes
input CreatePostInput {
  title: String!
  content: String!
  tags: [String!]
}

Interfaces & Unions

# Interface — contrat partagé
interface Node {
  id: ID!
}

type User implements Node {
  id: ID!
  name: String!
}

# Union — un champ qui peut renvoyer plusieurs types distincts
union SearchResult = User | Post | Comment

type Query {
  search(term: String!): [SearchResult!]!
}
💡
À retenir : la syntaxe du nullable String = nullable. String! = obligatoire. [String] = liste nullable d'éléments nullables. [String!]! = liste obligatoire dont chaque élément est obligatoire. C'est une question piège classique en entretien.
04

Queries — Lire des données

Une query GraphQL décrit la forme exacte de la réponse souhaitée. Le serveur renvoie un JSON qui mime la structure de la requête.

📥 Requête

query GetUser {
  user(id: "42") {
    name
    email
    posts {
      title
    }
  }
}

📤 Réponse

{
  "data": {
    "user": {
      "name": "Marie Dupont",
      "email": "marie@x.fr",
      "posts": [
        { "title": "GraphQL 101" }
      ]
    }
  }
}

Alias — éviter les collisions de noms

Indispensable quand vous appelez le même champ avec des arguments différents :

query {
  recent: posts(limit: 5, orderBy: DATE) {
    title
  }
  popular: posts(limit: 5, orderBy: VIEWS) {
    title
  }
}

Arguments & Variables

Ne jamais interpoler les valeurs dynamiques dans la query — utiliser des variables :

GraphQL Query
query GetUser($id: ID!, $postLimit: Int = 10) {
  user(id: $id) {
    name
    posts(limit: $postLimit) {
      title
    }
  }
}
JSON Variables
{
  "id": "42",
  "postLimit": 5
}
🛡️
Sécurité : utilisez TOUJOURS des variables Concaténer des valeurs dans la query c'est l'équivalent GraphQL d'une SQL injection. Les variables sont validées par le typage du schema.
05

Mutations — Modifier des données

Les mutations sont syntaxiquement identiques aux queries, mais sémantiquement différentes : elles indiquent une intention d'écriture. Le serveur les exécute en série, contrairement aux queries qui peuvent s'exécuter en parallèle.

Pattern create / update / delete

mutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {
    id
    title
    createdAt
    author {
      name
    }
  }
}

Variables

{
  "input": {
    "title": "Mon premier post",
    "content": "Hello, world!",
    "tags": ["intro", "graphql"]
  }
}
✨
Bonne pratique : retournez l'entité modifiée Toujours faire renvoyer l'objet créé/modifié par la mutation — ça permet au client de mettre à jour son cache (Apollo) sans refetch.

Pattern Result/Error (typage des erreurs métier)

Plutôt que de balancer une erreur générique, modélisez les erreurs comme des types de premier ordre :

union CreatePostResult = Post | ValidationError | NotAuthorized

type ValidationError {
  field: String!
  message: String!
}

type NotAuthorized {
  message: String!
}

type Mutation {
  createPost(input: CreatePostInput!): CreatePostResult!
}

Le client utilise alors __typename et des inline fragments pour réagir :

mutation {
  createPost(input: { title: "", content: "..." }) {
    __typename
    ... on Post { id title }
    ... on ValidationError { field message }
    ... on NotAuthorized { message }
  }
}

Subscriptions — Temps réel

Les subscriptions ouvrent un canal persistant (généralement WebSocket) entre client et serveur. Le serveur pousse les évènements au client à chaque déclenchement.

Client React
useSubscription
Serveur
PubSub.publish

📡 Connexion WebSocket persistante via graphql-ws

📐 Schéma

type Subscription {
  postAdded(channelId: ID): Post!
  commentLive(postId: ID!): Comment!
}

🎧 Côté client

subscription OnPostAdded {
  postAdded {
    id
    title
    author { name }
  }
}

Côté Node.js — Apollo Server avec PubSub

Node.js resolvers.js
import { PubSub } from 'graphql-subscriptions';

const pubsub = new PubSub();
const POST_ADDED = 'POST_ADDED';

export const resolvers = {
  Mutation: {
    createPost: async (_, { input }, { db }) => {
      const post = await db.posts.create(input);
      pubsub.publish(POST_ADDED, { postAdded: post });
      return post;
    }
  },
  Subscription: {
    postAdded: {
      subscribe: () => pubsub.asyncIterator([POST_ADDED])
    }
  }
};
07

Fragments & Directives

Des outils essentiels pour rendre les requêtes maintenables et conditionnelles.

Fragments — la DRY de GraphQL

fragment UserCard on User {
  id
  name
  avatar
  role
}

query FeedPage {
  posts {
    title
    author { ...UserCard }
    comments {
      text
      author { ...UserCard }
    }
  }
}

Côté React, les fragments permettent de colocaliser les données avec le composant qui les utilise — chaque composant déclare ses besoins, le parent compose.

Directives intégrées

query GetUser($includeEmail: Boolean!, $skipPosts: Boolean!) {
  user(id: "42") {
    name
    email @include(if: $includeEmail)
    posts @skip(if: $skipPosts) {
      title
    }
  }
}

Directives custom (côté schema)

directive @auth(role: Role!) on FIELD_DEFINITION
directive @deprecated(reason: String) on FIELD_DEFINITION

type Query {
  adminPanel: String! @auth(role: ADMIN)
  oldField: String @deprecated(reason: "Use newField")
}

Serveur Node.js — Apollo Server

Apollo Server est le standard de facto. Yoga (The Guild) est une alternative légère. Les resolvers sont des fonctions qui peuplent les champs du schema avec des données.

Setup minimal

Node.js server.js
import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

const typeDefs = `#graphql
  type Query {
    hello: String!
    user(id: ID!): User
  }
  type User { id: ID! name: String! }
`;

const resolvers = {
  Query: {
    hello: () => 'World',
    user: (_parent, { id }, ctx) => ctx.db.users.findById(id)
  }
};

const server = new ApolloServer({ typeDefs, resolvers });

const { url } = await startStandaloneServer(server, {
  context: async ({ req }) => ({
    db,
    user: await getUserFromToken(req.headers.authorization)
  }),
  listen: { port: 4000 }
});

console.log(`🚀 Server ready at ${url}`);

L'anatomie d'un resolver

Tout resolver reçoit 4 arguments :

fieldName: (parent, args, context, info) => {
  // parent  : résultat du resolver parent (ou undefined à la racine)
  // args    : arguments passés au champ (ex: { id: "42" })
  // context : objet partagé créé par requête (auth, dataloaders, db...)
  // info    : AST de la requête, schéma, path, fragments...
}

Resolvers par type — éviter le N+1

Node.js resolvers.js
export const resolvers = {
  Query: {
    posts: (_, __, { db }) => db.posts.findAll()
  },

  // Pour CHAQUE post retourné, ce resolver tournera
  Post: {
    // ❌ N+1 : 1 query pour les posts + N queries pour les auteurs
    author: (post, _, { db }) => db.users.findById(post.authorId),

    // ✅ DataLoader : batch + cache par requête
    author: (post, _, { loaders }) => loaders.user.load(post.authorId)
  }
};
🚨
Le problème N+1 — LA question d'entretien Si une query retourne 100 posts et que chaque post déclenche une requête SQL pour récupérer son auteur, vous faites 101 requêtes. DataLoader bufferise les load(id) sur un même tick d'event loop, puis exécute UNE seule requête WHERE id IN (...). Solution incontournable.

DataLoader — implémentation

Node.js loaders.js
import DataLoader from 'dataloader';

export const createLoaders = (db) => ({
  user: new DataLoader(async (ids) => {
    const users = await db.users.findByIds(ids);
    // IMPORTANT: réordonner pour matcher l'ordre des ids
    const map = new Map(users.map(u => [u.id, u]));
    return ids.map(id => map.get(id));
  })
});

// Dans le context d'Apollo Server
context: () => ({ db, loaders: createLoaders(db) })

Client React — Apollo Client

Apollo Client gère pour vous : exécution des requêtes, cache normalisé (par __typename + id), gestion d'état asynchrone, optimistic UI, refetch.

Setup & ApolloProvider

React main.jsx
import { ApolloClient, InMemoryCache, ApolloProvider, createHttpLink } from '@apollo/client';
import { setContext } from '@apollo/client/link/context';

const httpLink = createHttpLink({ uri: '/graphql' });

const authLink = setContext((_, { headers }) => ({
  headers: { ...headers, authorization: `Bearer ${getToken()}` }
}));

const client = new ApolloClient({
  link: authLink.concat(httpLink),
  cache: new InMemoryCache()
});

root.render(
  <ApolloProvider client={client}>
    <App />
  </ApolloProvider>
);

useQuery — lecture de données

React UserProfile.jsx
import { useQuery, gql } from '@apollo/client';

const GET_USER = gql`
  query GetUser($id: ID!) {
    user(id: $id) {
      id
      name
      posts { id title }
    }
  }
`;

function UserProfile({ id }) {
  const { data, loading, error } = useQuery(GET_USER, {
    variables: { id },
    fetchPolicy: 'cache-first' // défaut
  });

  if (loading) return <Spinner />;
  if (error) return <Error err={error} />;

  return <div>{data.user.name}</div>;
}

useMutation — écriture & mise à jour du cache

React CreatePost.jsx
const CREATE_POST = gql`
  mutation CreatePost($input: CreatePostInput!) {
    createPost(input: $input) {
      id title createdAt
    }
  }
`;

function CreatePost() {
  const [createPost, { loading }] = useMutation(CREATE_POST, {

    // Option 1 : refetch — simple mais coûteux
    refetchQueries: [{ query: GET_POSTS }],

    // Option 2 : update — chirurgical
    update(cache, { data: { createPost } }) {
      cache.modify({
        fields: {
          posts(existingRefs = []) {
            const newRef = cache.writeFragment({
              data: createPost,
              fragment: gql`fragment NewPost on Post { id title }`
            });
            return [newRef, ...existingRefs];
          }
        }
      });
    },

    // Option 3 : optimistic — UI instantanée
    optimisticResponse: { createPost: { __typename: 'Post', id: 'temp', ... } }
  });

  return <button onClick={() => createPost({ variables: { input } })}>Publier</button>;
}

Le cache normalisé

Apollo identifie chaque entité par __typename + id (ou _id) et stocke un objet plat. Mettre à jour User:42 propage automatiquement à toutes les queries qui y font référence.

// Cache après deux queries différentes :
{
  "User:42": { __typename: "User", id: "42", name: "Marie" },
  "Post:101": { __typename: "Post", id: "101", author: { __ref: "User:42" } },
  "Post:102": { __typename: "Post", id: "102", author: { __ref: "User:42" } }
}

Fetch policies — à connaître

PolicyComportement
cache-firstCache si dispo, sinon network. Défaut.
cache-and-networkCache immédiat, puis revalide via network. UI ultra-rapide.
network-onlyToujours réseau. Met à jour le cache.
no-cacheToujours réseau. N'écrit pas le cache (data sensibles).
cache-onlyLit uniquement le cache. Throw si absent.

Sujets avancés & pièges d'entretien

Les questions où on sépare le candidat junior du senior.

Pagination — Relay-style cursors

Plus robuste que offset/limit (pas de doublon ni de saut quand des entrées s'insèrent) :

type PostConnection {
  edges: [PostEdge!]!
  pageInfo: PageInfo!
}
type PostEdge {
  cursor: String!
  node: Post!
}
type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}

type Query {
  posts(first: Int!, after: String): PostConnection!
}

Sécurité — limiter les requêtes abusives

  • Depth limiting : refuser les requêtes > 7 niveaux d'imbrication (graphql-depth-limit).
  • Cost analysis : assigner un "coût" à chaque champ, rejeter au-dessus d'un budget (graphql-cost-analysis).
  • Persisted queries : le client envoie un hash, le serveur ne reconnaît que les requêtes pré-enregistrées.
  • Désactiver l'introspection en production (sauf si API publique).
  • Rate limiting par IP/user, comme tout autre endpoint.

Authentification & autorisation

Pattern recommandé : auth dans le context, autorisation dans les resolvers (ou via une directive @auth) :

// Dans le context
context: async ({ req }) => {
  const user = await verifyJWT(req.headers.authorization);
  return { user, db };
}

// Dans le resolver
Mutation: {
  deletePost: (_, { id }, { user, db }) => {
    if (!user) throw new GraphQLError('Auth required', {
      extensions: { code: 'UNAUTHENTICATED' }
    });
    if (user.role !== 'ADMIN') throw new GraphQLError('Forbidden');
    return db.posts.delete(id);
  }
}

Federation & microservices

Apollo Federation permet de composer plusieurs sub-graphes (un par microservice) en un super-graphe unifié exposé au client. Une équipe = un sub-graphe. Le routeur fédéré orchestre les requêtes cross-services.

Codegen — typage de bout en bout

graphql-codegen lit votre schema + vos requêtes .graphql et génère :

  • Les types TypeScript de chaque entité du schema.
  • Des hooks Apollo typés (useGetUserQuery, etc.) — plus de any.
  • Des types pour les resolvers côté serveur.

Top 5 questions pièges en entretien
  1. "GraphQL est-il toujours mieux que REST ?" — Non. Cache HTTP, simplicité, monitoring : REST gagne sur les APIs simples.
  2. "Comment évite-t-on le N+1 ?" — DataLoader. Batching + caching par requête.
  3. "Pourquoi toujours HTTP 200 ?" — Une réponse peut contenir des données partielles ET des erreurs simultanément.
  4. "Comment gère-t-on le versioning ?" — On ne version pas, on évolue : on ajoute, on déprécie via @deprecated, on supprime quand plus utilisé.
  5. "Quels sont les risques sécurité spécifiques ?" — Requêtes profondes, introspection en prod, IDs séquentiels exposés, manque de rate limiting par champ.
