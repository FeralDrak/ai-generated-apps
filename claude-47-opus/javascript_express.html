Qu'est-ce qu'Express ? 01 — Fondamentaux

Express est un framework web minimaliste, non-opinionated et middleware-driven pour Node.js. Il ne fait presque rien tout seul — c'est précisément sa force.

v4.x stable v5.x stable depuis 2024 ~3 KB de surface API Sponsor : OpenJS Foundation

Le mental model

Une application Express est essentiellement une pile de middlewares qui transforment ou répondent à un objet req (Request) avant de produire un res (Response). Tout est middleware, y compris les routes.

Pourquoi Express dans une stack moderne ?

  • Standard de facto de l'écosystème Node.js (Nest, Strapi, et d'autres tournent dessus).
  • Surface API minuscule : 5 méthodes principales (use, get, post, listen, Router) suffisent à 80% des cas.
  • Composabilité via middlewares — la même API gère logging, auth, validation, fichiers statiques, etc.
  • Liberté totale : aucune opinion sur ORM, validation, structure de dossiers, DI.
⚠ À retenir pour l'entretien

Express est non-opinionated (contrairement à NestJS ou Adonis). Cela veut dire qu'on construit l'architecture soi-même : c'est une force pour les petits projets, et une faiblesse pour les gros (d'où l'apparition de frameworks au-dessus).

Hello World

const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.send('Hello World!');
});

app.listen(3000, () => console.log('http://localhost:3000'));

Application & Serveur 02 — Fondamentaux

Comprendre la différence entre l'app Express et le serveur HTTP de Node est un classique d'entretien.

app n'est pas un serveur

Quand tu fais express(), tu obtiens une fonction (oui, une fonction !) qui est aussi un objet avec des méthodes. Cette fonction est compatible avec la signature attendue par http.createServer() : (req, res) => ....

const http = require('http');
const express = require('express');

const app = express();           // app est une fonction (req, res, next)

// Forme courte (Express crée le serveur en interne) :
app.listen(3000);

// Forme longue, utile pour HTTPS, WebSockets, tests :
const server = http.createServer(app);
server.listen(3000);
💡 Pourquoi ça compte ?

Pour brancher Socket.io, faire du HTTPS, ou tester avec supertest sans démarrer un vrai port, tu passes app directement — pas app.listen().

Routing 03 — Fondamentaux

Définir comment l'app répond à une combinaison URL + méthode HTTP. C'est le 80% de ce que tu écris.

Méthodes HTTP

app.get('/users', handler);       // GET /users
app.post('/users', handler);      // POST /users
app.put('/users/:id', handler);   // PUT /users/42
app.patch('/users/:id', handler); // PATCH /users/42
app.delete('/users/:id', handler);// DELETE /users/42

app.all('/admin/*', requireAdmin);// toutes méthodes sur ce path

Path patterns

PatternMatch
/usersExact
/users/:idParamètre nommé → req.params.id
/users/:id/posts/:postIdPlusieurs params
/files/*Wildcard (Express 4 : *, Express 5 : {*splat})
/ab?cdacd ou abcd (Express 4 seulement)
/.+\\.(jpg|png)$/Regex
⚠ Breaking change Express 5

Express 5 remplace path-to-regexp v0.x par v8. Les wildcards * deviennent {*name}, les groupes optionnels (...)? sont supprimés. Si tu vois TypeError: Missing parameter name au démarrage après un upgrade, c'est ça.

app.route() — chaining

app.route('/users/:id')
  .get((req, res) => res.json(getUser(req.params.id)))
  .put((req, res) => res.json(updateUser(req.params.id, req.body)))
  .delete((req, res) => { deleteUser(req.params.id); res.sendStatus(204); });

Ordre de matching

Les routes sont évaluées dans l'ordre de déclaration. La première qui matche gagne (sauf si elle appelle next()). Conséquence : route spécifique avant route générique.

// ✅ BON
app.get('/users/me', handler);     // matché en premier
app.get('/users/:id', handler);

// ❌ MAUVAIS — /users/me ne sera jamais atteint
app.get('/users/:id', handler);   // :id = "me"
app.get('/users/me', handler);

Middleware 04 — Fondamentaux

Le concept central d'Express. Tout est middleware, y compris les routes et la gestion d'erreur.

Signature

function middleware(req, res, next) {
  // 1. Lire/modifier req
  // 2. Lire/modifier res
  // 3. Soit appeler next() pour passer au suivant
  //    Soit terminer la réponse avec res.send/json/end
  next();
}
🔥 La règle d'or

Chaque requête doit produire exactement une réponse. Soit tu appelles next(), soit tu termines avec res.send/json/end/redirect — jamais les deux. Sinon : Error: Cannot set headers after they are sent to the client.

Les 5 types de middleware

TypeSignatureExemple
Application-levelapp.use(fn)app.use(logger)
Router-levelrouter.use(fn)Sur un sous-Router
Route-levelapp.get(path, fn)Handler de route
Error-handling(err, req, res, next)4 args = erreur
Built-in / 3rd-party—express.json(), cors()

Ordre = TOUT

app.use(logger());          // 1. log toute requête
app.use(express.json());     // 2. parse JSON → req.body
app.use(cors());             // 3. CORS headers
app.use('/api', requireAuth); // 4. auth seulement sur /api/*
app.use('/api', apiRoutes);   // 5. routes API
app.use(notFoundHandler);    // 6. 404 catch-all
app.use(errorHandler);       // 7. erreurs (4 args)

Mounter un middleware sur un chemin

// Appliqué partout :
app.use(logger);

// Appliqué seulement aux URLs commençant par /api :
app.use('/api', apiMiddleware);

// Plusieurs middlewares en chaîne sur une route :
app.post('/posts', requireAuth, validatePost, createPost);

Middleware "usine"

Pattern très répandu : une fonction qui retourne un middleware, pour le paramétrer.

function requireRole(role) {
  return (req, res, next) => {
    if (req.user?.role !== role) return res.sendStatus(403);
    next();
  };
}

app.delete('/admin/users/:id', requireRole('admin'), deleteUser);

Chaining typique

💡 Piège fréquent

req.query et req.params contiennent toujours des strings. req.query.page sur ?page=2 donne '2', pas 2. Tu dois parser/valider toi-même (zod, joi, parseInt...).

Router modulaire 06 — Patterns

express.Router() = une mini-app qui peut être montée sur un préfixe. L'outil de modularisation principal.

Pattern de base

// routes/users.js
const router = express.Router();

router.use(requireAuth);                // s'applique à toutes les routes du router

router.get('/', listUsers);            // GET  /users
router.get('/:id', getUser);            // GET  /users/:id
router.post('/', createUser);          // POST /users

module.exports = router;

// app.js
const usersRouter = require('./routes/users');
app.use('/users', usersRouter);

Nesting

Un Router peut monter d'autres Routers : composition sans limite.

app.use('/api/v1', v1Router);
v1Router.use('/users', usersRouter);
v1Router.use('/posts', postsRouter);
// → GET /api/v1/users/:id

mergeParams

Par défaut, un sous-router ne voit pas les params du parent. Active mergeParams pour les hériter.

// /users/:userId/posts/:postId
const postsRouter = express.Router({ mergeParams: true });

postsRouter.get('/:postId', (req, res) => {
  // req.params.userId est dispo grâce à mergeParams
  res.json({ user: req.params.userId, post: req.params.postId });
});

usersRouter.use('/:userId/posts', postsRouter);

router.param() — hook sur un param

S'exécute une fois quand un param est présent dans la route. Pratique pour préchargement.

router.param('userId', async (req, res, next, id) => {
  try {
    req.user = await User.findById(id);
    if (!req.user) return res.sendStatus(404);
    next();
  } catch (err) { next(err); }
});

router.get('/users/:userId', (req, res) => res.json(req.user));

Params, Query, Body 07 — Patterns

Les trois sources d'entrée d'une requête HTTP, et comment Express les expose.

req.params

Variables nommées dans le path. Toujours string.

// Route : /users/:id
// URL   : /users/42
req.params.id // '42'

req.query

Tout ce qui suit le ?. Parsé par qs (nested objects ok).

// URL : ?page=2&filter[role]=admin
req.query.page          // '2'
req.query.filter.role   // 'admin'

req.body (JSON)

Nécessite express.json() en amont.

app.use(express.json({ limit: '1mb' }));

app.post('/users', (req, res) => {
  req.body.name // 'Alice'
});

req.body (form-urlencoded)

Pour formulaires HTML classiques.

app.use(express.urlencoded({ extended: true }));

Multipart / fichiers

Express ne parse pas le multipart nativement. Use multer :

const multer = require('multer');
const upload = multer({ dest: 'uploads/' });

app.post('/avatar', upload.single('file'), (req, res) => {
  req.file       // { filename, path, mimetype, size, ... }
  req.body.title // autres champs du formulaire
});

Validation

Express n'a pas de validation built-in. Choix typiques : zod, joi, express-validator, yup. Pattern recommandé : un middleware de validation par route.

const { z } = require('zod');

const userSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  age: z.number().int().min(18),
});

const validate = (schema) => (req, res, next) => {
  const result = schema.safeParse(req.body);
  if (!result.success) return res.status(400).json(result.error);
  req.body = result.data;
  next();
};

app.post('/users', validate(userSchema), createUser);

Gestion d'erreurs 08 — Patterns

Un middleware d'erreur a 4 arguments au lieu de 3. C'est ainsi qu'Express le reconnaît.

L'error-handling middleware

// ⚠ DOIT être déclaré APRÈS toutes les routes
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.status || 500).json({
    error: err.message || 'Internal Server Error',
  });
});

Comment "lever" une erreur

Tu n'utilises jamais throw dans un callback async sans le rattraper, sinon Express ne le verra pas. Tu passes l'erreur à next().

app.get('/users/:id', (req, res, next) => {
  User.findById(req.params.id)
    .then(user => {
      if (!user) {
        const err = new Error('Not found');
        err.status = 404;
        return next(err);          // → saute aux error handlers
      }
      res.json(user);
    })
    .catch(next);                  // idiome classique
});

Express 4 vs 5 : async

✅ Express 5

Une fonction async dont la promise rejette est automatiquement envoyée au middleware d'erreur. Plus besoin de wrapper.

⚠ Express 4

Une promise rejetée dans un handler async n'est pas attrapée. Tu dois wrapper ou utiliser express-async-errors.

// Wrapper "asyncHandler" classique en Express 4 :
const ah = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

app.get('/users/:id', ah(async (req, res) => {
  const user = await User.findById(req.params.id);
  if (!user) throw Object.assign(new Error('Not found'), { status: 404 });
  res.json(user);
}));

404 catch-all

Placé juste avant le error handler, après toutes les routes.

app.use((req, res, next) => {
  res.status(404).json({ error: 'Not Found' });
});

Async / await 09 — Patterns

Le piège n°1 d'Express en entretien. Sache exactement comment async se comporte selon la version.

Le piège classique

// Express 4 — DANGER 💥
app.get('/data', async (req, res) => {
  const data = await fetchData();   // si ça reject... ?
  res.json(data);
});
// → UnhandledPromiseRejection, la requête pend pour toujours,
// → le client timeout côté Nginx/ELB, fuite de descripteurs.

Solutions

  1. Upgrade vers Express 5 — supporte async nativement.
  2. Wrap chaque handler avec asyncHandler ou express-async-handler.
  3. Mettre require('express-async-errors') tout en haut du fichier — patch global qui rend Express 4 async-safe.
  4. Try/catch + next(err) explicite dans chaque handler.
// Option 3 — la plus discrète :
require('express-async-errors');          // monkey-patch global
const express = require('express');

app.get('/data', async (req, res) => {
  res.json(await fetchData());        // reject → error middleware ✅
});
💡 Question type entretien

« Que se passe-t-il si tu fais throw new Error() dans un handler async d'Express 4 sans wrapper ? »

Réponse : la promise rejette, Express ne le voit pas (il ne fait pas .catch sur le retour du handler), le middleware d'erreur n'est pas appelé, et Node lève un UnhandledPromiseRejection. Le client reste pendu jusqu'au timeout.

Sécurité 10 — Production

Express en prod sans hardening = surface d'attaque maximale. Le mini-checklist à connaître.

Le starter "prod-grade"

const express      = require('express');
const helmet       = require('helmet');          // headers sécurité
const cors         = require('cors');            // CORS
const rateLimit    = require('express-rate-limit');
const compression  = require('compression');     // gzip
const morgan       = require('morgan');          // access logs

const app = express();

app.set('trust proxy', 1);                     // derrière nginx/ELB
app.disable('x-powered-by');                    // cache le fingerprint

app.use(helmet());
app.use(cors({ origin: process.env.WEB_ORIGIN, credentials: true }));
app.use(compression());
app.use(morgan('combined'));
app.use(express.json({ limit: '1mb' }));      // limite la taille
app.use(rateLimit({ windowMs: 60_000, max: 100 }));

Sécurité par sujet

RisqueMitigation
XSS via templatesÉchapper par défaut (Pug, EJS le font); ne pas utiliser !{} ou <%-%> sans précaution
CSRF (cookies de session)csurf (deprecated) ou same-site strict cookies + custom header
Headers manquantshelmet (CSP, HSTS, X-Frame-Options...)
NoSQL injectionexpress-mongo-sanitize, valider types avec zod
Brute forceexpress-rate-limit + express-slow-down
Payload énorme → DoSexpress.json({ limit: '1mb' })
HPP (HTTP Param Pollution)hpp middleware
Secrets en clairdotenv + ne JAMAIS commit .env
Cookies non-sécuriséshttpOnly: true, secure: true, sameSite: 'lax'
AuthJWT signé (HS256+) ou sessions Redis avec express-session
🔥 trust proxy

Si ton app est derrière un proxy (nginx, ELB, Cloudflare) sans app.set('trust proxy', 1) :

  • req.ip retourne l'IP du proxy, pas du client
  • req.protocol retourne 'http' même en HTTPS
  • Le rate-limiter limite tout le monde sur la même IP (celle du LB)

Performance 11 — Production

Express n'est pas le plus rapide, mais beaucoup de problèmes viennent de patterns naïfs, pas du framework.

Quick wins

  • Compression : compression() middleware → divise la bande passante texte par ~5.
  • NODE_ENV=production : désactive logs de stack en clair, active des optimisations internes (templates, cache view).
  • Cluster / PM2 : Node mono-thread → un process par CPU. pm2 start app.js -i max.
  • Keep-Alive : déjà activé par défaut, mais vérifier le timeout côté LB.
  • Streaming : pour gros fichiers, res.sendFile ou un Readable.pipe(res) au lieu de tout charger en mémoire.

Pièges courants

⚠ Synchronous I/O

fs.readFileSync, JSON.parse de fichier énorme, bcrypt.hashSync → bloquent l'event loop. Toute requête en cours attend. Toujours préférer les versions async ou worker_threads.

⚠ Middleware lourd appliqué globalement

app.use(parseHugeBody) exécute le parser pour chaque requête, même GET /health. Mount-le sur le path concerné : app.use('/upload', parseHugeBody).

Profilage

app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    console.log(`${req.method} ${req.path} ${res.statusCode} ${ms.toFixed(1)}ms`);
  });
  next();
});

💡 Pitch d'entretien

« J'aime Express pour sa simplicité et son écosystème mature. Pour un projet plus structuré ou typé, je passerais à NestJS qui en réutilise le moteur. Pour de la perf critique ou des contrats JSON Schema, Fastify. Et pour de l'edge, Hono. »

Express ↔ NestJS

NestJS utilise Express sous le capot par défaut (ou Fastify en opt-in). Tu retrouves donc tout ce que tu sais d'Express (middlewares, req/res, statuts...) dans Nest, encapsulé derrière des décorateurs et un système d'injection de dépendances.

Playground : pipeline de middleware 14 — Pratique

Construis une requête, observe l'ordre exact dans lequel les middlewares s'exécutent. C'est le mental model qu'il faut avoir en entretien.

Le code de l'app simulée
const app = express();

app.use(logger);          // MW1
app.use(express.json()); // MW2
app.use('/api', requireAuth); // MW3 (sur /api/*)

app.get('/health', (req, res) =>
  res.json({ ok: true }));

app.get('/api/users/:id',
  validateId, fetchUser, sendUser);

app.post('/api/users',
  validateBody, createUser);

app.use(notFound);        // catch 404
app.use(errorHandler);    // catch erreurs
Simule une requête
Cliquer "Envoyer" pour exécuter le pipeline…
💡 Essaie
  • GET /health sans token → passe (pas sous /api)
  • GET /api/users/42 sans token → bloqué par requireAuth (401)
  • GET /api/users/42 + header Authorization: Bearer abc → passe par tout le pipeline
  • GET /api/users/abc + token → 400 (validateId échoue)
  • GET /nope + token → 404 (not found handler)
